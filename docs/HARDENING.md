# Production hardening V1

Проверка выполнена относительно первого MVP `0a618c7`. Дизайн и набор продуктовых функций сохранены. Это инженерный отчёт о проверенном корпусе, а не обещание совместимости с любым существующим DOCX.

## Подтверждённые дефекты и исправления

- `\w` в регулярном выражении не охватывал русские окончания: «Список использованных источников» и последующие записи попадали под обычное форматирование. Библиография теперь сохраняется и получает ручное замечание.
- Семантика Caption/Title/Bibliography терялась у производных стилей без `outlineLvl`. Учитывается цепочка `basedOn`; неизвестные и циклические цепочки не угадываются.
- Верхние/нижние индексы, позиционированные и специальные символьные runs могли получить обычный размер. Их оформление сохраняется; неподдерживаемые font slots и неоднозначные фрагменты требуют ручной проверки.
- Титульные строки с пунктуацией и явные титульные блоки могли получить отступ/выравнивание основного текста. Добавлены осторожные ограничения; наличие настоящего BodyText не позволяет объявить весь первый раздел титульным.
- Сетка строк раздела может переопределять визуальный межстрочный интервал. Активная привязка проверяется вручную; отсутствующий тип сетки не считается активным.
- Пропущенные проверки отступа/разделов ранее участвовали в оценке как успешные. Оценка теперь относится к реально проверенным параметрам, рядом указан охват; при отсутствии проверок отображается «—».
- ZIP-парсер раньше не сверял все локальные размеры/CRC/descriptors и допускал некоторые неоднозначные имена/пересечения. Эти случаи отклоняются до трансформации.
- Сохраняемые relationships и XML проверялись слабее основного документа. Проверяются все связи пакета, MIME-объявленные XML-части, пространства имён, объявления XML и ограничения сложности. Внешние ресурсы не запрашиваются.
- Легальное имя части `__proto__` выявило ограничение объектного ZIP writer в fflate. Для такого редкого пакета используется проверенный streaming writer; отдельная регрессия проверяет неизменность частей с особыми именами.
- Отменённый `File.arrayBuffer()` мог воскресить старый документ. Идентификатор операции теперь назначается до чтения файла. Ошибки передачи/десериализации Worker освобождают Worker и таймер сразу.
- Blob-скачивание делало лишнюю полную копию. Теперь используется view точного диапазона; Blob сам создаёт неизменяемый snapshot. Копия при отправке в Worker сохранена намеренно: исходный буфер нужен для повторных/выборочных операций и восстановления после ошибки.
- Проверка зависимостей выявила уязвимости старого dev test runner и его transitive dependencies. Vitest обновлён до исправленной версии с полным повторным прогоном; это не добавляет зависимостей в браузерный runtime.

## Корпус и независимость проверок

`tests/corpus/academic.ts` создаёт реальный OPC-пакет с тремя разделами portrait → landscape → portrait, разными полями, first/even/default headers/footers, нумерацией страниц, TOC/REF fields, bookmarks, footnotes/endnotes, hyperlinks, nested numbering, merged/nested tables, inline/anchored images, Office Math, captions, revisions, comments, символьными/абзацными стилями и embedded XLSX. Отдельный корпус содержит 6 000 абзацев / 12 000 runs. Есть Cyrillic, Latin, Unicode, NBSP, soft hyphen и пустые абзацы.

Тестируется цепочка original → analyse → fix → ZIP save → reopen → analyse. Проверяются сам текст и whitespace, набор и байты неизменяемых частей, relationships, media/embedded hashes, защищённые XML-поддеревья, фактические значения свойств и повторная обработка. Повторный анализ собственным parser не заменяет прямые проверки свойств.

Уровни доказательств различаются:

1. **Структура:** Python `zipfile` независимо проверяет CRC/ZIP, ElementTree — каждый XML, отдельный проход — ссылки и идентификаторы. `python-docx`, когда установлен, отдельно открывает документ и читает разделы/таблицы.
2. **LibreOffice:** headless открытие, пересохранение DOCX, повторное открытие пересохранённого пакета и PDF export; проверяются наличие текста и ориентации страниц. Использованная версия записывается в JSON-отчёт. В текущей среде установлен LibreOfficeDev 26.8 alpha: это ограничение конкретной проверки.
3. **Microsoft Word:** не запускался. Совместимость с Word и совпадение его пагинации не подтверждены.

```sh
npm test
npm run build
npm run test:e2e
npm run test:compatibility
npm audit --audit-level=moderate
```

Последняя compatibility-команда требует Python 3 и LibreOffice. Для PDF-проверок полезны `pdfinfo` и `pdftotext`; проверка через `python-docx` дополнительная. Приложению эти инструменты не нужны. Корпус и отчёты по умолчанию находятся в `/tmp/norma-hardening/corpus`, вне репозитория. CI дополнительно запускает независимые ZIP/XML/relationship checks; наличие workflow не означает, что конкретный GitHub Actions run уже завершился.

## Производительность

Генератор `scripts/generate-performance-fixtures.py` (нужен Pillow) создаёт настоящие DOCX с 1 000 абзацев и валидным PNG с несжимаемыми пикселями, около 1, 5, 10 и 19.9 МиБ. Это image-heavy корпус; выводы нельзя переносить на произвольную сложность XML или мобильное устройство.

`scripts/benchmark-browser.mjs` запускает новый Chromium для каждого из трёх повторов. Замеры до/после используют одну и ту же машину и файлы, immutable production build первой версии и production build V1, без параллельных suites. Измеряются Worker round trip и пользовательское событие → результат, heartbeat основного потока с периодом 16 мс, RSS дерева процессов Chromium с выборкой примерно 40 мс.

RSS суммирует shared pages повторно и не равен JS heap или точной эксклюзивной памяти. Выборка может пропустить короткие пики. Абсолютные значения и прирост над idle — приблизительные process-memory показатели, а не гарантированные лимиты для всех устройств.

Измерено в Linux, Node.js 24.19.0, Chromium 154.0.8037.57. После замеров результаты всех четырёх размеров были отдельно скачаны из production build и открыты через Python `zipfile`, ElementTree и `python-docx`: текст и все остальные ZIP-части сохранились, исправленные свойства изменились. На этих больших файлах LibreOffice не запускался; Office-проверка относится к сложному academic-корпусу.

В таблице медианы трёх Worker round trips и трёх приращений RSS. UI gap — худший интервал heartbeat из повторов, а не время полной блокировки. На 1 МиБ дополнительная валидация сделала обработку медленнее; результат не скрыт. На 19.9 МиБ исправление ускорилось примерно в 2.2 раза. Полные сырые замеры: `performance-before.json`, `performance-after.json`.

Отдельный browser microbenchmark Blob на 20 МиБ: медиана конструктора со старой явной копией ~37.6 мс, с view ~17.4 мс. Это отдельный тест, а не ускорение всего workflow.

Оптимизация ZIP применяется только к известным image formats, которые уже хранились без сжатия либо с отношением compressed/uncompressed ≥ 0.95. Хорошо сжимаемые части продолжают сжиматься; исходные байты частей не меняются. Нельзя просто отключить сжатие у любого файла `.png`: это могло бы резко увеличить выходной DOCX.

Повторить замеры: собрать два checkout-снимка и поднять их production preview на разных портах, затем последовательно выполнить:

```sh
npm run benchmark:fixtures
npm run benchmark:browser -- http://127.0.0.1:4174 /tmp/norma-hardening/performance-before.json
npm run benchmark:browser -- http://127.0.0.1:4173 /tmp/norma-hardening/performance-after.json
```

## Сохранение frontend

App разделён на четыре содержательных UI-компонента, hook жизненного цикла документа и небольшие helpers. CSS разбит по областям с сохранением порядка каскада. Нет новых UI frameworks. Отдельные E2E воспроизводят медленное чтение/отмену/новую загрузку, отключённое и повреждённое хранилище, `inert`/focus trap и нулевой охват. Оценка и сообщения о ручной проверке уточнены намеренно.

Пиксельное сравнение immutable MVP и V1: пустое состояние и настройки на 1440×1050 и 390×844, локальные шрифты загружены, reduced motion. Во всех четырёх снимках различий 0 пикселей (`visual-comparison.json`). Текст отчёта об охвате изменён намеренно и в это сравнение не входит.

## Оставшиеся границы перед публичным запуском

- Это не полный валидатор всех OOXML XSD и не антивирус. Embedded packages/OLE сохраняются как непрозрачные вложения и не исполняются; внешние ссылки сохраняются, но их содержимое не проверяется.
- Определение неразмеченных заголовков/титульного листа остаётся эвристикой. Документы без надёжных стилей, специальные scripts/шрифты, grids и рецензирование требуют ручной проверки.
- Изменение полей/шрифта закономерно меняет переносы и пагинацию. Наличие шрифта на машине получателя, совпадение рендеринга и полное соответствие методичке не гарантируются.
- Архивы ZIP64, защищённые/подписанные/macro-enabled документы и слишком сложные пакеты отклоняются. Лимиты интерфейса и parser — защита от расхода ресурсов, а не обещание обработать любой документ меньше лимита.
- Перед широким запуском нужен дополнительный обезличенный корпус реальных работ, проверки в установленном Microsoft Word и на Safari/Firefox/мобильных устройствах с меньшим объёмом памяти. В этой среде проверялся Chromium, включая mobile viewport; он не заменяет реальные iOS/Android устройства.
